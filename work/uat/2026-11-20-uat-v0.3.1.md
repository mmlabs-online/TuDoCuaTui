## UAT-1 → BUG-010: Chrome autofills the saved account password into the AI "API key" field

| Field | Value |
|---|---|
| Type | bug |
| Severity | S2 |
| Priority | P1 |
| Size | XS |
| Areas | security, ui |
| Gate | plan-approval (secrets handling → High tier) |
| Found in | production v0.3.1 (UAT 2026-11-20) |

### Report
When the AI settings modal opens (header button "AI"), the "API key" field is already filled and shows the error
"Key không đúng định dạng (20–256 ký tự, không có khoảng trắng)", although the user typed nothing.
The DOM shows `input.matches(':autofill') === true`: Chrome's password manager has put the saved login password for
this site into the field.

### Environment
- Chrome with a saved password for `tudocuatui.mmlabs.online` (the user signs in with email + password).

### Steps to reproduce
1. Sign in and let Chrome save the password.
2. Click the "AI" button (Cài đặt) in the top bar.

### Expected
- The API key field is empty (the hint "Đã lưu: ••••XXXX. Để trống nếu giữ key cũ." stays correct).
- The browser never offers or fills the account password into this field.

### Actual
- The field holds the autofilled account password and shows a format error at once.
- In this case the password is shorter than 20 characters, so validation blocks saving. **If a user's password is
  20 characters or more with no spaces, it passes validation, and "Lưu" stores the account password as the AI key and
  then sends it to Claude/Gemini as an API key** (a credential leak to a third party), and replaces the real key.

### Root cause
`src/features/settings/AiSettingsModal.tsx:164-165` renders `<input type="password" autoComplete="off">`. Chrome
ignores `autocomplete="off"` on password inputs and autofills the saved login.

### Scope / fix idea
- Use `autoComplete="new-password"` (and a distinct `name`, e.g. `ai-api-key`) or a `type="text"` field with
  CSS masking, so the password manager does not treat it as the login password.
- Optional hardening: do not submit a value the browser autofilled (`:autofill`) without a user edit.
- Test: render the modal and check the input has `autocomplete="new-password"`; e2e if possible.

## UAT-2 → BUG-011: Never-worn items show "hơn 1 năm", and a brand-new item counts as "≥ 90 ngày chưa mặc"

| Field | Value |
|---|---|
| Type | bug |
| Severity | S3 |
| Priority | P2 |
| Size | S |
| Areas | ui, logic |
| Gate | none (needs Ming's call on the label, see Scope) |
| Found in | production v0.3.1 (UAT 2026-11-20) |

### Report
70 of 71 items have never been worn. Every one of their cards shows "👕 0× · hơn 1 năm". An item created during the
test, one second earlier, also showed "0× · hơn 1 năm", and the stat card "≥ 90 ngày chưa mặc" went from 70 to 71.
The app has existed for about two weeks, so "more than a year" is never true for these items.

### Steps to reproduce
1. Click "Thêm món đồ", enter a name, save.
2. Look at the new card and at the stat cards.

### Expected
- A never-worn item's card says something like "chưa mặc" (or the time since it was added).
- The "≥ 90 ngày chưa mặc" card and the hero line "Hôm nay có N món lâu chưa mặc" do not count an item added today
  as unworn for 90 days.

### Actual
- Card: "0× · hơn 1 năm". Stat "≥ 90 ngày chưa mặc": +1. "Chưa mặc lần nào": +1. Hero: "Hôm nay có 71 món lâu chưa mặc".
- The two stat cards show the same number (70) because one includes the other.

### Root cause
`src/features/items/filters.ts:7` — `ageInDays = daysSince(date, now) ?? 999`. An empty `lastWorn` becomes 999 days,
so `ItemCard.tsx:39` prints "hơn 1 năm" and `isStale` (`filters.ts:9`) is true.
`docs/feature-list.md:44` defines stale as "not worn for 90 days or more, **or never worn**", so the count follows the
spec; the label "≥ 90 ngày chưa mặc" and the card text do not.

### Scope / fix idea
- Card: when `lastWorn` is empty, show "chưa mặc" instead of a day count.
- Stats: Ming to choose — (a) relabel the card (e.g. "Lâu chưa mặc"), or (b) count only worn items ≥ 90 days, or use
  `createdAt` for never-worn items so new items are not stale for 90 days. Proposed default: (b) with `createdAt`.

## UAT-3 → BUG-012: Outfit suggestion says "Mùa Đông" in hot weather

| Field | Value |
|---|---|
| Type | bug |
| Severity | S3 |
| Priority | P2 |
| Size | XS |
| Areas | ui, logic |
| Gate | none |
| Found in | production v0.3.1 (UAT 2026-11-20) |

### Report
"Hôm nay mặc gì?" with weather "TP. Hồ Chí Minh · 25–34°C · Mưa 84%" shows the heading "Mùa Đông", while each outfit
has the tag "Trời nóng". The two contradict each other on the same screen.

### Steps to reproduce
1. Click "Hôm nay mặc gì?" on 2026-11-20.
2. Select "TP. Hồ Chí Minh" in "Thời tiết".

### Expected
- The heading matches what drove the suggestion (e.g. "Trời nóng · 25–34°C"), or the season label is hidden or
  adjusted when the weather overrides it. Southern cities have no winter.

### Actual
- "Mùa Đông" is shown with "Trời nóng" tags. With weather "Tắt" it also shows "Mùa Đông" for every city.

### Root cause
`src/features/outfits/suggest.ts:7-28` — `seasonOf()` maps the calendar month to a season (Nov → Đông) for the whole
country. `eligibility()` (`suggest.ts:96-102`) correctly swaps Đông for Hạ when it is hot, but the returned
`season` (shown as `Mùa ${s}`, `outfits/copy.ts:7`) is still the calendar season.

### Scope / fix idea
- Show the season actually used (the `wanted` list), or hide the season heading when weather is on.

## UAT-4 → BUG-013: Cold weather (9–12 °C) still suggests an off-shoulder party dress and heels, with no warning

| Field | Value |
|---|---|
| Type | bug |
| Severity | S3 |
| Priority | P3 |
| Size | S |
| Areas | logic |
| Gate | none |
| Found in | production v0.3.1 (UAT 2026-11-20) |

### Report
Weather "Sa Pa · 9–12°C · Mưa 100%" → Bộ 1 is "Váy đi tiệc trễ vai xanh + Giày cao gót phom trơn 9p trắng +
Áo cardigan voan đen + Khăn choàng lụa", tagged "Trời lạnh", "Có thể mưa".

### Steps to reproduce
1. "Hôm nay mặc gì?" → Thời tiết = "Sa Pa".

### Expected
- Warmer items first (long sleeves, long dresses, outer layers), or a visible note such as "Tủ đồ chưa có đồ mùa
  Đông — gợi ý có thể chưa phù hợp" when nothing fits.

### Actual
- Summer and party items are suggested with no warning. The wardrobe has 0 items tagged "Đông".

### Root cause
`suggest.ts:111-114` — when no item of a role fits the wanted seasons, the pool silently falls back to all items of
that role (`pools[role] = fit.length ? fit : all`). The rain flag only adds a tag.

### Scope / fix idea
- Keep the fallback, but return a flag and show a note in the modal; optionally rank items without "Hạ" higher
  when it is cold.

## UAT-8 → BUG-017: Full-size photos used for small thumbnails; slow rendering seen (needs investigation)

| Field | Value |
|---|---|
| Type | bug |
| Severity | S3 |
| Priority | P3 |
| Size | M |
| Areas | performance |
| Found in | production v0.3.1 (UAT 2026-11-20) |

### Report
- The grid and hero images are ~1180–1200 px (≈1.4 MP) blobs from `/api/photos/:id`, shown at ~110–180 px
  (average about 6× larger than shown).
- 36 `.wear-pill` elements use `backdrop-filter: blur(6px)`, plus `.topbar` (16px) and `.modal-backdrop` (4px).
- During the test, after scrolling the grid, screenshot capture timed out (30 s) four times and `requestAnimationFrame`
  ran at only 2–4 fps, with **no long tasks** on the main thread. The cost is in painting or compositing, not in JS.

### Caveat
Not confirmed as app-only: the browser window may have been throttled. Re-check with DevTools Performance on a
normal machine and on a mid-range phone before fixing.

### Scope / fix idea
- Serve a thumbnail size (e.g. 360 px) for cards and the hero collage, and keep the full size for the editor.
- Try removing `backdrop-filter` on the wear pills (a solid semi-transparent background looks almost the same).

## Minor UX notes (not bugs yet)

1. Searching "đầm" (or "dam") returns 12 items, while the "Đầm" category has 19. Search does not match the category
   name; 7 dresses are named "Váy …". Consider adding the category to the search text.
2. Clicking the "≥ 90 ngày chưa mặc" card filters the list (70 results), but the only sign is the "Xoá bộ lọc"
   button. Show an active-filter chip.
3. Long item names are cut off with "…" and have no `title` tooltip.
4. "Vị trí lưu trữ" filter opens an empty list when there are no locations. Hide it or show "Chưa có vị trí".
5. "Mặc nhiều nhất" changes to the most recent item when counts tie (1 vs 1). The tie-break is not defined.
6. The sort select lets the user pick the placeholder option "Sắp xếp" (empty value); the result is the same as "Mới thêm".
7. The same accessory ("Túi tote kẻ sọc…") appears in 2 of 3 suggested outfits on most refreshes. With only 2
   accessories this is expected, but variety rules could avoid it.

## Passed

- Page load: `/api/items` and `/api/locations` → 200, no console errors.
- Category chip counts add up to 71; chip filters (e.g. Đầm = 19).
- Search: accented and unaccented both work; empty state "Không tìm thấy món đồ" and "Xoá bộ lọc".
- Filters: status, season, color give consistent counts; sorts "Mới thêm", "Tên A→Z", "Mặc nhiều nhất",
  "Lâu chưa mặc", "Giá cao → thấp".
- Infinite scroll loads 36 → 48 → 60 → 71.
- Editor: unsaved-change guard on "Huỷ" and on Esc ("Bỏ thay đổi?"); discard does not save.
- Validation: empty name, spaces-only name, negative price ("Giá không được âm"); purchase date `max` = today.
- Create → stats update (72 items, 150.000 ₫); "Mặc hôm nay" → "1× · hôm nay"; "−1" does not go below 0.
- "Nhân bản" opens a new form with "(bản sao)" and copies the price; save → 73 items, 300.000 ₫.
- Delete: custom confirm "Xoá món đồ này?" → toast "Đã xoá món đồ"; totals back to 71 / 0 ₫.
- "Hôm nay mặc gì?": weather from Open-Meteo per city, "Đổi gợi ý" changes the outfits, the city choice is kept
  after closing and reopening, Esc closes.
- Dark mode toggles and toggles back. Export and Import modals open and close (no file was downloaded or uploaded).
