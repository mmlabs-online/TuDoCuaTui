## Findings
1. **`drive.file` scope is enough.** Folders are files; the app can create a folder (metadata-only POST, `mimeType: application/vnd.google-apps.folder`, `parents: [root]`) and see it and its contents. The root was created by `drive-connect.mjs` with the same client. Access is per file per client, so files stay accessible after a move.
2. **Moving files:** `PATCH /drive/v3/files/{id}?addParents=<sub>&removeParents=<root>&fields=id,parents`, body may carry `{"appProperties":{"userId":"<uuid>"}}` — one call moves and tags. My Drive files have exactly one parent; `addParents` alone is rejected (probably `cannotAddParent`, verify). `appProperties` PATCH merges keys. Retry is safe. Unsure what `removeParents` does for a parent the file no longer has → read `parents` first and skip files already in place.
3. **Reads, replaces, deletes need no logic change** (`getMedia(id)`, `deleteFile(id)` by Drive id, which survives a move). Only `createFile` changes (`parentId` arg, `userId` tag).
4. **The sweep breaks:** `taggedFilesQuery` filters on `'<root>' in parents`, so subfolder files are not listed; and the "missing file" check would report every migrated photo as missing. The fake Drive's list handler accepts only that exact query.
5. **Race safety must come from the app:** Drive has no uniqueness on names/appProperties and its search index lags; lookup-then-create is not safe alone.
6. **Constraints:** no transaction across Drive IO (pool `max: 5`); `withMaintenance` is SELECT-only for `"photo-sweep"`, pinned by `scoping.test.ts` to `db.js` and `photo-sweep.js`.
7. **Single instance today** (one container, one Drive client per process); the only other folder creator would be the migration script running alongside.

## Recommendations
- **R-A. Folder resolver `server/driveFolders.js`**, shared by `photos.js` and the script: in-flight `Map<userId, Promise<folderId>>` (single-flight → AC1), resolved `Map<userId, folderId>` (never cache failures). Lookup query `'<root>' in parents and mimeType = 'application/vnd.google-apps.folder' and trashed = false and appProperties has { key='userId' and value='<uuid>' }`; on several results pick oldest `createdTime` (id tie-break). Create with name `<user_id>`, `appProperties {app:"tudo-folder", userId}`. Interpolate only after `isUuid` / `FOLDER_RE`.
- **R-B. Cache in memory only, no DB (default).** No migration/RLS change; duplicate folder is cosmetic (reads/deletes by file id); cost one `files.list` per user per process lifetime. Alternative: `drive_folders(user_id pk, folder_id unique)` with `owner_only` RLS, "create in Drive then `insert … on conflict do nothing returning`", loser deletes its empty folder — choose only for multiple instances or zero duplicates with the script running live.
- **R-C. Upload path:** resolve folder after the quota pre-check, before `createFile`; `createFile({ ..., parentId, appProperties: { app, photoId, itemId, userId } })`. Resolve failure → existing mapping (`drive_auth`/`drive_forbidden`/`drive_folder_not_found` → 503, else 502), existing refund. No silent fallback to the flat folder. `createFile` `drive_not_found` (folder deleted by hand) → drop cache entry, fail this request, no retry. Logs stay without folder ids.
- **R-D. `drive.js`:** `createFolder` (not retried), `moveFile(id, {addParent, removeParent, appProperties})` (retried), `getParents(id)` or `parents` in `listFiles` fields, `subfoldersQuery(rootId)`, `userFolderQuery(rootId, userId)`; `listFiles` stays the only list primitive; add `cannotAddParent` to `REASONS` if the smoke confirms.
- **R-E. Sweep lists each folder, keeps the parent filter:** a query without a parent filter would include files of another deployment using the same client/Drive with a different `DRIVE_FOLDER_ID`, and `--apply` would delete them. Instead: list subfolders of the root (one level), run `taggedFilesQuery(id)` for root + each subfolder with global `MAX_PAGES`/token guards, build `listed`/`present` from the union. Report-only `mismatch <photoId>` when `appProperties.userId` ≠ row `user_id`. Never delete folders.
- **R-F. Script `server/photo-relocate.js`:** `[--apply] [--max-move 1..10000, default 100]`, exit 0/1/2, dry-run default. `checkFolder`; list root-level tagged files only (moved files drop out → idempotent/resumable); read `id, user_id, drive_file_id` across users; match by `drive_file_id`; no row → `unreferenced`, tag mismatch → `mismatch` (skip); else resolve owner folder (dry-run: lookup only, `would create folder for user <uuid>`) and one move+tag PATCH; 404 → `gone`. Guards: sweep-style refusal when nothing listed is referenced; `--max-move` cap. Sequential calls; existing backoff. Output only photo ids, user ids and counts. DB read via `withMaintenance(pool, "photo-sweep", …)` (no migration, misleading name; scoping allow-list update) or a new task name with a policy migration (Ming's call). README runbook: smoke → dry-run → `--apply` until `would_move 0` → sweep dry-run (0 missing).
- **R-G. Extend `drive-smoke.js`:** temp folder → file in root → move into folder → read → delete file → delete folder; proves the move live before `--apply`.
- **R-H. Fake Drive + tests:** folder create, PATCH move (reject `addParents` alone), folder lookup and subfolder list queries (strict regexes). AC1 two parallel PUTs → one folder; AC2 read/delete in subfolder and root; AC3 dry-run/apply/second run 0/unreferenced stays/`--max-move` resumes; AC4 subfolder orphan, migrated not missing; AC5 sentinels absent.

## Risks
Duplicate folders across processes (cosmetic; oldest-folder rule converges); search index lag; live upload during migration is safe (404 → `gone`); a folder trashed/deleted by hand trashes/loses its photos — document "never delete user folders"; prod/dev sharing one client and Drive (reason for R-E); first-upload latency negligible; unverified Drive details caught by R-G.
